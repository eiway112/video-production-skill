## 数字规范自检（规定）

每个 Scene 的**旁白全文**定稿后、提交用户审核节点前逐条自检。机器门为 preflight 检查 13（`narration_digits`，`preflight_check.py:1199-1213`：render 模式命中即阻断、audit 模式降级 warning）；本节是**撰写侧**自检——门禁通过不替代本节（白名单只管例外，可读性由人裁定）：

- [ ] 旁白与字幕中的数值一律阿拉伯数字："30小时"、"5%"、"20元"；禁止"三十小时"、"百分之五"形态
- [ ] 例外仅成语（如"三心二意"）与序数（如"第三"）；白名单唯一权威源 `程序文件/配置/config/quality/narration_digits_rules.json`（`idiom_whitelist`），追加例外改该文件或经 config 项目级 `narration_digits_whitelist` 声明——**不得在分镜/旁白里 ad-hoc 开口子**
- [ ] 带 json 两张单位表（`primary_units` / `extended_units`）内单位的量化数值必须全部阿拉伯（此为检查 13 裁定面）；表外单位的中文数字组合不在门禁裁定面，撰写侧按可读性裁定，但不得借此为表内量化项保留中文数字
- [ ] 字幕与旁白同源：旁白数值改动后同步核对字幕数值，只改一侧即分叉
- [ ] **数字后面别接单字**：数字与后接汉字之间在旁白里必然带空格（"第 3 关""4 关"），该形态是 TTS 断词犹豫的高发点——实测（`agent-decision-map` 2026-10-12，qwen cosyvoice-v3-flash rate +5%，口径见下）全片"数字 + 空格 + 汉字"句中边界 **13 处有 2 处**出现 **0.28s / 0.40s** 的真实静音（成片 `silencedetect=-35dB` 独立复核，非对齐读数），而**真·句中且原文两字之间无任何字符**的纯汉字边界 **862 处仅 3 处**达 0.2s（0.35%）、中位 0.000s 对数字处的 0.060s——**概率约 44 倍**。两处都被用户听成"不必要的停顿"。同片内"4 道关卡"处 gap 仅 0.04s，可直接用作替代写法。**统计口径（三条，缺一即读数不可比）**：gap ＝ 字符级 `chars[i][0] − chars[i-1][1]`（后字符起口减前字符收尾，非句间）；基线只纳入"两侧皆汉字且归一化字符流之间不留任何原文字符"，带标点者单列（该片标点后边界 84 处 81 处 ≥0.2s＝96.4%，中位 0.400s，属设计内句读）；数字侧带空格的单字才计入"点名形态"。**本数由脚本复算，不得手算**（同一条统计本轮手算出过 911/25、868/4、862/3 三个数，差别全在"基线纳入哪些边界"，前两个已作废；复算脚本 `过程产物/临时产物/_取证/20261012/recount_pause_baseline.py`，取证件有保留期，口径以上述三条为准）。**写法**：补出一个音节——"第 3 关"→"第三道关卡"或"3 道关卡"，让引擎读到双音节词。属**撰写侧自检、非门禁**（该形态概率低，设成阻断会把正常项目误杀；符合"观感问题优先改写法、不新增代码门禁"的既有裁定）

## 断词与停顿自检（规定）

2026-10-13 用户对多支成片给出同一条口播反馈："断句停顿的节奏（停顿和标点）把握不准"。复盘实测后根因分两类，**都不是停顿阈值的问题**，且都在撰写侧可预防。机器面为 `程序文件/脚本/narration_pause_precheck.py`（零渲染／零 TTS／零 ASR，判据住 `config/quality/narration_prosody_rules.json`；**2026-11-06 起其绝对阈命中不再是纯描述面**——timeline 步末按四态裁定，实测时刻的低于下限判 FAIL 并阻断渲染，见 `agents.md` 门禁表`_enforce_punctuation_pauses` 与 `_pause_gate_verdict` 两行）；本节是撰写侧自检，脚本无点名不替代本节（脚本只认已登记的形状）。

- [ ] **量词后紧接的字会不会与量词构成另一个词**：该处若没有标点，强制停顿机制根本无从作用——引擎按词切分，"红线至少一条带触发条件"被读成"一条带"（条带＝strip）、"第 3.1.3 条管线分离"被读成"条管线"。**写法**：在语义边界补标点，或把该短语从枚举里拆成整句、换动词（"写明"代替"带"）。判据面同形扫描见脚本 `merge_risk`。
- [ ] **逗号与顿号给出的停顿现在由机器兜到 0.25s，但写法仍不得靠它制造层次**：段间强制（`audio_sync_rules.json → sentence_pause.min_seconds`＝0.4）作用在**字幕段边界**；2026-11-06 起另有**句内标点强制面**（`intra_pause_enforce.min_seconds`＝0.25）在波形层把低于下限的逗号/顿号/冒号位点补齐到该下限（跨项目实测：六支项目 429 个段间位点零未达标，而段内标点 43 个低于 0.2s 可听阈——差别只在有没有接进生效路径）。**这条兜底不改变撰写侧的两条取舍**：① 它只补到 0.25s，要**更长**的强调停顿仍须作者声明`pause_marks`（见下节），机器不替作者决定语气；② 它只在 ASR 实测时刻上动刀，插值时刻（`matched=0`）一律拒补并点名——所以旁白写得越密、标点用得越含糊，落到未测档的比例越高。同一片实测停顿中位／最低值：句号 0.40~0.46／0.28、分号 0.44／0.20、冒号 0.26~0.40／0.00、逗号 0.34／0.16、顿号 0.30／0.14、无标点 0.00。**读法**：句号/分号比逗号/顿号可靠一档；而"拆句"也不等于拿到强制停顿——分段函数会把相邻短句贪心合并回同一段（合计 ≤40 字即合并），只有合并后仍成为段边界的那条缝才有 0.40s 下限。
- [ ] **一句只放一个信息点，句内标点不要超过两个**（2026-11-06 由用户口播反馈复盘实测）：本片初稿 8 场 239 字、单场最多一句三标点，用户点名的『翻图集、约 3 个专业开会，大约两天』即出自这种密度。密度高时引擎在同一次调用里还要接着说，标点处的释放被压薄——强制面能把间隙补到下限，但补不出"这句说完了"的语气。**写法**：长句拆短句、一句一个信息点，需要强调的停顿用 `pause_marks` 声明而不是堆逗号。该写法不构成控制面（理由见下面「完整语义单位被切开」条的跨时间实测），控制面是强制面＋裁定面，本条只是把落到未测档的概率压低。
- [ ] **一条长枚举不要塞进一句**：单段 ≥28 字且含 ≥3 个顿号即"读成一团"的高发形态（本轮命中该形状的段落与用户点名处重合）。**写法**：每项自带一句，或减少每项内容。
- [ ] **完整语义单位被引擎从中间切开（2026-11-05 用户点名，撰写侧可预防、但不可预期）**：形状＝**两个同义或相邻的双字词并成四字而不带标点**（`评价验收`、`计量计价`、`强制底线`），引擎把它读成自己的枚举，在**词内**留出与项间停顿同档的静音——实测 `价|验` 0.32s、`量|计` 0.28s、`制|底` 0.30s、`三|大` 0.32s，谷底 -26~-37 dBFS。听感后果不是"有停顿"，而是**分组歧义**：一条五项的枚举被听成七项。
  **写法**：四字并列项要么真的拆成两项（各带顿号，并接受项数变化），要么加连接词或改成不形成 2+2 的形状（`验收与评价`／`把验收和计价分开`）。
  **但改写不构成控制面（本轮实测，非取舍声明）**：同文本连合成三次 wav 的 sha256 逐字节相同（引擎对给定输入确定），而 10 月交付波形里 0.30s 的那处、11 月按**逐字未改的整场旁白**重合成后为 0.00s——跨时间不确定；单句粒度测出的"这处干净"在整场粒度上会翻转。故**不得据一次小样合成结论判定"改好了"**，也不得把"改文案"写成修复手段。
  **可靠面**：① 渲染前看 `narration_pause_precheck` 的**第三桶**（timeline 步自动打印，与两桶同处，专点名无标点处的可听停顿）；② ~~波形修剪面可代处理~~ **已于同日判否，不得启用**：第四轮用该面对已交付成片音轨出三档静音对照件，用户试听裁定"越改越糟，出现音频被不正常切断的突兀感"——压缩判据（5ms 帧峰值 < -30 dBFS）在 66.2s 上命中 36~42 处（每 1.7 秒一刀），而参考片同口径句内可闻间隙仅 0.7 处/分钟，说明多数"静音段"是清辅音与韵尾的能量跌落而非停顿，切点落进音素内部。`intra_pause_trim` 维持缺省关闭、不排期启用，且**不得再对已验收成片出修补式对照件**。裁定与三条纪律见 `外部参考片实测与借鉴裁定_20261105.md` §十一 与 `agents.md` Tier 2「观感与听感类改动的三条纪律」。判据、阈值、能量腿全部住 `程序文件/脚本/intra_pause.py` 与 `audio_sync_rules.json → intra_pause_trim`，本节不复述数值。**已知边界**：本面只治"下一轮合成的波形"，已交付成片不回改（一场改动即一次全量渲染，且交付槽位受保护）。
- [ ] **"数字 + 空格 + 单字"是偶发形态，两次实测给出相反读数**：`agent-decision-map` 13 处有 2 处出现 0.28s／0.40s 真实静音；`standard-system-explainer` 同形 18 处中位 0.04s、最大 0.16s、**0 处**达 0.2s；而 2026-11-05 在同一支 `standard-system-explainer` 的 `_修订05` 交付波形上，`支撑结论的是 3 大支柱` 的 `三|大` 实测 **0.32s**（谷底 -26.5 dB，两侧 -13.1／-17.3）。三条互不顶替——该形态**偶发且随整段上下文翻转**（同一句单送引擎 0.00s，按生产粒度整场 101 字送引擎即 0.30s）。写法上仍按上一条规避，但**不得把"改文案"当控制面**，见下面「完整语义单位被切开」条。
- [ ] **极短句不要放在场景中段当收束**（2026-10-21 实证）：同一片两处人耳点名的"句界局促"（`照着验收，就用。`／`…门禁、发布。`）形状相同——**≤10 字的极短句 + 句号 + 本场后面还有话**。引擎在同一次调用内还要接着说时几乎不释放：该句生产占用 **225ms**，同文本独立合成是 **390ms**；切点处实测 **−17.8 dBFS**，前句末字与下句首字之间**没有能量谷**。**且句号本身不保证留白**——同场实测顿号处 630ms、句号处 0ms，引擎的停顿分配与语义边界无稳定对应。下游的切点、淡入淡出、停顿阈值都救不回来：它们只能削弱能量，不能造出边界。**写法（按稳妥度）**：① 把短句扩到 12 字以上，让引擎有释放余量；② 并进下一句、用逗号连成长句（代价是丢掉那个句号的强调）；③ 挪到场景末尾（本场在此结束才会真正释放）。**限定**：样本 2 处、同一片，属高风险形态提示而非硬判据；`narration_pause_precheck.py` 不认这一形状，不会点名。

### 段内停顿的显式声明（`pause_marks`，2026-10-14 接线批）

**引擎边界（2026-11-07 用户裁定）**：本节只对 **CosyVoice（qwen）** 成立。`tts_engine: "elevenlabs"` 的项目**不写 `pause_marks`**——该引擎不支持 SSML `<break>`，声明与它相遇会由 `pause_marks.plan_scene` 直接抛错（不静默忽略）。裁定取向是**弃声明**、接受该引擎自身的韵律，而不是另建一套"切分+补静音"的停顿机制（两套并存即两份真相）。切引擎时把该项目的 `pause_marks` 整段删掉；波形层的句间 0.4s／句内 0.25s 强制与引擎无关，照常生效。

上面第 2 条"不要指望逗号与顿号给出停顿"只描述了一半事实：**引擎侧其实有一个直接控制面**，本批已把它接进生效链。判据、取值区间、每场上限、缺省与标定读数全部住 `程序文件/配置/config/quality/audio_sync_rules.json → pause_declaration` 与 `程序文件/脚本/pause_marks.py`，本节只定"在哪儿写、写成什么样、什么时候该写"，不复述数值（复述即第二真相源）。

**语法**——声明住在 narration.json 的场景对象上，**不写进旁白文本**：

```json
{
  "scene_id": "s3",
  "narration": "先把口径对齐，再谈落地节奏。",
  "pause_marks": [
    {"after": "对齐", "ms": 500}
  ]
}
```

- `after`：旁白里**逐字出现**的词（归一化口径与词级 cue 同源，取首次命中；同一词在场内出现多次会 WARN 点名，因为"我想停的是哪一次"机器无从判断）。这条停顿**永远不会发生在锚词落不到的地方**，所以预检直接阻断而不是静默去掉。
- `ms`：停顿毫秒数，越界即报错**不做夹取**——夹取等于把作者要的节奏改成机器能接受的值，而作者看不出来。
- 为什么不用旁白内标记串（如 `…对齐[[+0.5s]]，…`）：旁白文本的消费者有六处（字幕分段、ASR 对齐、词级 cue、数字 lint、分段度量、交付说明），写进文本意味着六处都要记得剥离，六处就是六套口径。结构化字段让六个消费者逐字不变。

**什么时候该写**：只在"必须停而标点给不出"的位点——语义边界、长枚举的项与项之间、量词与后一字会粘成另一个词的那条缝。这是**补充面不是替代面**：上一条自检（漏标点／长枚举塞一句）仍是第一防线，声明只用于文字已经正确、节奏仍不对的位置。

### 停顿类缺陷的处置顺序（2026-11-06 两支竖屏项目实测后立）

上面各条把"有哪些面"讲清了，但没讲**看到点名时按什么顺序选**。这个缺口是有代价的：`_修订04` 先试了改写（把逗号改句号），修好了被点名的位点、却把另一处问号打回 0.00s；`_修订05` 才走声明面，一轮到位。按下面的顺序走可以省掉中间那一轮：

1. **先问该位点是不是字幕段边界**（取数＝`temp/_timeline_manifest.json` 的 `sentences[].text` 是否在此处断开）。
   - 是 → 波形层强制面本来就该管，实测仍 <0.4s 属机制未兑现，按缺陷上报，**不要靠改文案绕过**。
   - 否（被合并进同一段）→ 波形层**结构上看不见它**，只能走 ② 或 ③。
2. **文字本身是否正确**？
   - 正确、只是节奏不对 → **声明面 `pause_marks`**（唯一单调生效的段内控制面）。
   - 文字本身可改且改后语义不变 → 句号拆句；但须知道拆分未必成为段边界（分段函数会贪心合并短句，见上面第 2 条），**拆完必须复跑三桶确认**。
3. **被点名的是"不该停却停了"（第三桶）** → 上面两面都不适用：加任何标点只会更糟；修剪面已判否不启用。此时唯一诚实的处置是记录读数并交人耳，不得反复改写试探。
4. **加过声明后必须复跑 `--project`**：SSML 模式下未声明位点的节奏也会移动（权威节里写明），只看被修的那一处会漏掉新出现的连读——本仓两次实测到这种"修好一处、打回另一处"。

**听感类误读（多音字／近形字）没有机算复核面**：ASR 的句级文本是**向旁白原文回显**的，所以"某个字读错了"在 `sentences[].text` 上永远显示正确。此类缺陷只能由人耳发现，修法取**规避型改写**（换词避开该字），不得写成"重合成一次看能否读对"——同文本跨轮结果本就不确定。发现一处即登记一处到本节末尾的清单，供后续项目规避同形词。

已登记的误读位点（人耳一手，非机器读数）：

| 词 | 现象 | 规避写法 | 出处 |
|---|---|---|---|
| 构造 | "构"读成 rou | 「其余做法保持不变」 | 竖屏业务片 `_修订04`（用户 2026-11-06 听判） |

**项目级自动补位**：config 顶层 `pause_auto_enabled: true`（或 `audio.pause_auto_enabled`）让机器按形状阈值自己在枚举位点补停顿，受同一每场预算约束。缺省关闭的理由是实测的：开启＝机器替作者改朗读文本并加长片长（场景窗口由 TTS 时长驱动，级联到时长预算与全量渲染）。**作者声明与自动补位同时在场时，同位点以作者为准；作者声明超出上限时报错不截断**——写了停顿而拿到的音频没有，与 `bgm_source`／cue 那一族"静默降级"同形。

**适用范围**：仅 Qwen/CosyVoice 引擎（支持清单同样住权威节）。引擎不支持而声明在场 → 报错，禁止按另一套 SSML 语法猜测执行；引擎不支持而仅开了自动补位 → WARN 点名"本机制对本项目零动作"，因为这组合不破坏任何东西，但作者必须知道自己以为的事没发生。

## 叙事链自检（规定 · 撰写侧，无机器门）

2026-10-26 对一支 153s 参考产品片逐帧核对后立的规约，四条形态取自该片。**来源限定**：本仓没有"改前／改后"对照读数，故这是写法规约而非实测判据，不设门控——场与场之间是递进还是并列属语义判断，机算判据会大面积误杀（与"观感问题优先改写法、不新增代码门禁"同向）。

分镜定稿、提交用户审核节点前按顺序过四项：

- [ ] **每场首句能独立成立**：把各场首句依次抄出来单独读，不得依赖"这个／它／如上所述"回指上一场。回指的代价是漏听一场就连带丢掉后面几场的指代对象。
- [ ] **场与场之间是递进不是并列（只裁论证主线，并列枚举可豁免但须声明）**：主线上的相邻两场，判断法＝调换顺序若语义仍然通顺，说明它们是并列要点而非论证——此时二选一：改结构做出递进（写得出"因为上一场说了 X，所以这一场才要问 Y"），或在本节写明"此处为并列枚举、不构成递进"并给每场各自的承载形态。**沉默的并列才是病灶，显式对齐的并列不是**——本章节的多项能力列举本就该并列，不要为了凑递进把它们硬串成因果。
- [ ] **承接写具体**：每场分镜表的「承接」行须落在具体图元／命名／位置上（如"上一场的四层色带下移一层作为本场底图"）。"继续向前推进""延续上一场氛围"这类描述等于没写。
- [ ] **末句可被单独截图**：全片最后一句是结论而非过渡，不得以"综上所述／总而言之／以上就是"开头，不得含只在本片语境下成立的指代。判断法＝把末句单独发给没看过这片的人，他能否看懂并当作结论引用。（末句不受「断词与停顿自检」里"极短句不放场景中段"那条约束——本场在此结束，引擎才会真正释放。）

**与既有两节的分工**：数字规范自检管"念得对不对"，断词与停顿自检管"念得顺不顺"，本节管"讲得成不成一条线"。三者互不替代——前两节的机器面（preflight 检查 13 是门禁；`narration_pause_precheck.py` 的文本面只点名形状）通过，不构成本节通过。

| 画面活跃度 | 场景之间**不得整段冻住**：持续动效须挂在**信息层元素**上（随旁白推进的波形/进度、跟随讲解的高亮与画线、指向正在说的内容的操作光标、被念到的条目微位移），**装饰层慢呼吸不计入该项**——动画写在码上、落在背景光斑的数秒 yoyo 里，成片读数仍等于静止。分镜阶段逐场答一句"这一场正在说的那个元素怎么动"，答不出即该场只有静态排版，须补强调形态或改承载形态（见「结构化图形承载」行） | 设计判据，无代码门禁（同本表其余观感项，2026-10-10 常设裁定）。**怎么写**（A 组信息层／B 组装饰层的可抄骨架与两条风险）住 `新路径实施_踩坑清单与防范检查表.md` §八「持续动效模板」，本处不复述代码。**怎么自查**：完工报告 `data_sources.frame_occupancy.motion`（`frame_occupancy.measure_motion`，描述面不裁定）。2026-11-05 一支外部参考片实测给出本项存在的理由（同法静止占比 0.8% 对 69.3%／74.5%），并**第三次独立支撑"画面占用不设门禁"**——差距量在"画面是否在动"上，不在"画面有多满"上；口径、读数与对照腿见 `外部参考片实测与借鉴裁定_20261105.md` §2.1、§2.3-2.5、§七。**同日第二支（竖屏）参考片补三条，须一并读**：① 倍数按画布向取，竖屏对竖屏只有 2.4~3.5 倍，不得引用横屏那个量级；② 它**没有相机位移**（四角与固定水印区实测全静）却仍拿到 77.6% 在动 → 永动的路线不止"根元素慢位移"一条，把微动摊在**中带信息层元素＋内容区局部粒子层**更便宜且**有机会走增量渲染**；③ 观感上"卡点严丝合缝"经三个取数面证明来自**小变化频率**（193 次/分钟 对 本仓 37-71）而非对齐精度——**cue 精度面已无余量，放慢动画／加缓动曲线亦非正路**（该方向已被同法实测证伪）。见同文 §十三。"永动底"已给骨架但**未升为强制默认**，成本与风险见同文 §八、§五（含两条路线成本差） |
| 章级标识 | 分章的信息片（经验阈值：**≥4 章或 ≥5 分钟**）须有**常驻章级标识**＝章序号＋章名＋章进度刻度，固定在画面一角不动。三条约束：① 只用 `opacity` 做时间位切换，切换时刻**锚在既有 T-block 章起点**上；② 不加旁白、不改场景窗口、不引入第三类动画范式（它是画面层改动，不是内容改动）；③ 单章短片不强制——多一块常驻即多一块视觉噪声。动因：观众在中段问"这是第几件事"时画面必须答得上来，否则读作信息过载，而这类流失的病灶是**缺归属标识**而不是每场字数 | 设计判据，无代码门禁（同本表其余观感项）；分镜阶段先在「常设观感默认」本节把 13 场归 4–5 章、章名列表写进分镜表，再在 HTML 里落一个常驻元素。**注意它与增量渲染的关系（2026-11-05 按实测更正，此前写的是预期）**：章级标识按其定义放在**场景 div 之外**（固定在画面一角、跨场常驻），因此它的点亮语句按 `scene_patch_render.resolve_selector` 判 `selector-outside-scenes` → **必判全量渲染**。实证读数：`standard-system-explainer` `scene_patch = {verdict: FULL, reason: html-outside-scenes-changed, attempts: 5, hits: 0}`。故**按全量估成本才是稳妥做法**；"只加一个 opacity 时间位切换的元素就应走增量"那句预期不成立，它错在把"改动小"当成"可归属"。跨场**内容**图形请用下一行的锚＋生长写法（留在场景 div 内，可归属）。 |
| 跨场主图常驻（锚＋生长） | 分章的信息片（同档经验阈值：**≥4 章或 ≥5 分钟**）每章选**一张主图作锚**（剖面图／系统拓扑／流程主干），该章各场在它上面**生长**内容，而不是每场整块换一张图。分镜阶段逐章答一句"这一章的主图是什么、每场在上面长出哪一层"；答不出＝该章各场是并列卡片，观众读作"在换页"而非"在长知识"。写法三条：① 基形在**每场各画一份**、内联几何逐字相同、带契约属性 `data-anchor="<图形名>"`（同一名值＝同一张图）；② 生长层是本场自己的元素，时刻锚在本场 `T.sN`；③ **按章常驻，不按全片常驻**（覆盖场次过半即失去增量资格） | 设计判据，无代码门禁（同本表其余观感项）。**怎么自查**：完工报告 `data_sources.choreography.persist`（`choreography_profile.measure_persistence`，描述面不裁定——声明处数／覆盖场次与占比／几何不一致锚数／场景外实例数／**基形初始隐藏两条计数**：后者非 0＝那块图在成片里全程不存在，而这一格无阻断式门禁兜着）。可抄骨架（A5）与三条风险住 `新路径实施_踩坑清单与防范检查表.md` §八；两条常驻拓扑的**增量资格实测对撞**（场景外＝必判 FULL，场景内同位同形＝可归属且四条静态门禁零误杀）住 `外部参考片实测与借鉴裁定_20261105.md` §14.7 |
| 结构化图形承载 | 每个**信息场景**须有一个图形形态承载它的内容关系——流程（节点图/回流环）、层级（分层色带）、对比（同量纲条形）、序列（编号/代码块）、趋势之一；**纯卡片阵列不算承载**（卡片是容器，它装得下关系但不表达关系）。分镜阶段逐场写明"这一场画的是什么形"，写不出即说明该场内容还没被想清楚。取舍三条：① 图形上的数字必须来自旁白（口画一致，参考件里有而旁白没有的数据不引入，属取舍须在交付说明写明理由）；② 一场一个主形态，并置两类以上须有从属关系；③ **立体、模拟指针、同一内容换形态属"表现手段"，不替代承载形态**——一场仍须先答出"这场的形状是什么"，表现手段只负责把它演出来，先想特效再想形＝倒序，退化成装饰 | 设计判据，无代码门禁（同本表其余观感项）；五类承载形态、三类表现手段的可复制骨架与四条共用纪律住 `HyperFrames_HTML模板参考基准.md` §4.8，病灶实证与检查项见 `新路径实施_踩坑清单与防范检查表.md` §4.6。**手上有一支同素材／同类型的更好看的片子时，用其参考件对照法取形态**（抽 ≥12 帧逐帧问"这一帧的形状在我这版里有没有对应物"，取形状不取数据） |

> 本表各项的"要不要"由这里裁定，"怎么实现"一律回代码/配置权威源读——在此写死数值即第二个真相源，改代码不会改这里。

## 用户审核节点

以下内容需要用户确认后才能进入 HTML 制作：

1. **图文匹配**：每个场景引用的图片是否与旁白内容匹配？
2. **缺失素材**：标记为“ImageGen 生成”或“跳过”的场景是否可接受？
3. **时间节奏**：各场景时长分配是否合理？有没有太长或太短的？
4. **遗漏素材**：素材盘点中有哪些可用素材没有被分配？
5. **视觉风格**：深色/浅色主题选择、字号体系是否满意？

## config.json 生成（审核通过后执行）

分镜设计审核通过后，生成 config.json 作为渲染流水线输入：

```json
{
  "video_name": "{视频名}",
  "video_duration": {total_seconds},
  "voice": "zh-CN-YunxiNeural",
  "scenes": [
    {
      "id": "scene{N}",
      "narration": "{旁白全文}",
      "window": {start, end},
      "duration": {window_end - window_start}
    }
  ],
  "paths": {
    "html": "{project_name}/index.html",
    "output": "{output_path}"
  }
}
```

生成方式：
- 推荐：`python scene_config_generator.py --narrations narrations.txt --output config.json`
- 手写：AI 根据分镜设计的时间分配表直接生成

## 使用方式

```
Step 1: python asset_scanner.py --project {name}
Step 2: AI 阅读扫描结果 + SDL/旁白，填写本文档
Step 3: 用户审核分镜方案
Step 4: 审核通过 → AI 手写 HTML（参照 HyperFrames_HTML模板参考基准.md）
Step 5: 生成 config.json（scene_config_generator.py 或 AI 手写）
Step 6: preflight_check.py 预检 PASS
Step 7: pipeline_runner.py --config 渲染流水线
```
